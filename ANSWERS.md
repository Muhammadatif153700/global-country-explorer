Q1. How to Run

To run this project, Node.js (LTS version) must be installed on the system. After cloning or downloading the project, open the terminal inside the project folder and run the command npx serve .. This will start a local development server, and the application can be accessed by opening http://localhost:3000 in a modern web browser. Alternatively, the project can also be run using npx http-server . -p 8080 -o, which starts a server on port 8080 and automatically opens the browser. No API keys, environment variables, or additional configuration are required because the project uses fully public APIs, including REST Countries and Open-Meteo. The application can also be opened directly by double-clicking the index.html file, although some browsers may restrict API requests in file:// mode.

Q2. Stack Choice

This project is built using a simple and lightweight frontend stack consisting of HTML, CSS, and Vanilla JavaScript (ES6+), along with Leaflet.js for maps and Chart.js for visualizing weather data, both loaded via CDN. The reason for choosing this stack is to ensure maximum simplicity and zero setup complexity for the evaluator. The project runs instantly with a single command without requiring any build tools, package installation, or framework setup. All application logic, including API calls, filtering, sorting, error handling, and UI rendering, is implemented in a single JavaScript file, making it easy to read and evaluate. This approach keeps the project lightweight, transparent, and fast to execute. Frameworks like React or Angular were intentionally avoided because they introduce unnecessary build steps and dependencies that are not required for an API-focused assignment. Similarly, a backend solution like Python Flask was not used since the APIs are already publicly accessible and CORS-enabled, making a backend layer unnecessary.

Q3. One Real Edge Case

A key edge case handled in this project involves missing or incomplete geographic data returned by the REST Countries API. Some countries do not provide valid latlng or capitalInfo.latlng values, which are required for rendering the map and fetching live weather data. Without proper validation, this would result in runtime errors or broken UI components when attempting to access undefined coordinates. To handle this, the application checks whether valid latitude and longitude values exist before making any API calls or initializing the map. If the data is missing, the application gracefully skips the weather and map rendering instead of crashing. This ensures that the rest of the country details remain fully functional and the user experience is not interrupted.

Q4. AI Usage

AI tools such as ChatGPT and Gemini were used as development assistants during the project. They helped in suggesting suitable public APIs, structuring the initial application architecture, and providing guidance for implementing asynchronous fetch operations. AI was also used to understand how to integrate Open-Meteo weather data and Leaflet maps properly within a vanilla JavaScript environment. However, all core logic, including error handling, filtering, sorting, UI rendering, offline fallback handling, and API integration improvements, was manually implemented and modified. The AI-generated suggestions were not used directly without changes; instead, they were adapted and optimized to fit the project requirements and improve performance, readability, and reliability.

Q5. Honest Limitation / Improvement Scope

One limitation of the current implementation is that the offline fallback dataset includes only a small number of countries instead of the full global dataset. This means that in offline mode, the user does not get complete world coverage. This decision was made intentionally to keep the project lightweight and focused on live API usage rather than storing large static datasets. If more time were available, this could be improved by implementing localStorage caching of the full API response after the first successful load, allowing offline access to the complete dataset. Additionally, a service worker could be introduced to enable true offline-first functionality by caching API responses and serving them when the network is unavailable. Another improvement would be to optimize stored data by saving only essential fields such as name, coordinates, population, and flags to reduce storage usage and improve performance
